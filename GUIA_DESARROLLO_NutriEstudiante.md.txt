# FASE 0: Preparación del Entorno

## Paso 0.1: Instalar herramientas base

### Subpaso 0.1.1: Instalar Bun
- Visitar https://bun.sh
- Ejecutar el comando de instalación según tu sistema operativo
- Verificar instalación:
  ```bash
  bun --version
  ```

### Subpaso 0.1.2: Instalar Node.js y MongoDB
- Node.js LTS (se usa para herramientas complementarias si es necesario; Bun ejecuta el código).
- MongoDB local (`mongodb://127.0.0.1:27017/nutriestudiante`) o una base remota (Atlas).

## Paso 0.2: Estructura del repositorio

```
NutriEstudiante/
├── backend/     → API REST (Express + TypeScript + Mongoose)
├── frontend/    → SPA (React + TypeScript + Vite + MUI)
├── assets/      → recursos estáticos del proyecto
├── package.json → scripts raíz (concurrently para dev)
└── *.md.txt     → planificación y esta guía
```

## Paso 0.3: Scripts disponibles

Desde la raíz:

```bash
bun install                 # instala dependencias del monorepo
bun run dev                 # levanta backend y frontend a la vez
bun run dev:backend         # solo backend (http://localhost:4000)
bun run dev:frontend        # solo frontend (http://localhost:5173)
```

Dentro de `backend/`:

```bash
bun run seed                # crea el usuario admin + contenido inicial
bun run typecheck           # verifica tipos con tsc
```

Dentro de `frontend/`:

```bash
bun run lint                # oxlint
bun run build               # tsc -b + vite build
```

# FASE 1: Backend

## Paso 1.1: Configuración

- `src/config/index.ts` lee variables de entorno (`PORT`, `MONGODB_URI`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`).
- `src/config/db.ts` conecta a MongoDB con Mongoose.
- `src/index.ts` monta Express, Helmet, CORS y sirve `/uploads` como estático.
- Copiar `.env.example` a `.env` y ajustar los valores.

## Paso 1.2: Modelos (Mongoose)

- `User` → nombre, correo, contraseña (bcryptjs), edad, peso, estatura, sexo, rol (`user` | `admin`). La contraseña nunca se serializa a JSON.
- `Session` → sesión opaca por usuario: `tokenHash` (SHA-256 del token completo), `userId` y `expiresAt` (índice TTL que la borra al vencer).
- `WeightRecord` → registro de seguimiento (peso + fecha por usuario).
- `Recipe` → título, descripción, ingredientes, instrucciones, información nutricional e imagen.
- `Exercise` → nombre, descripción, duración, dificultad (`baja | media | alta`) e instrucciones.
- `Tip` → título y contenido.

> El IMC **no se almacena**: se deriva del peso y la estatura (`backend/src/utils/bmi.ts`).

## Paso 1.3: Autenticación y seguridad

- Registro, login y cambio de contraseña (`authController.ts`).
- Contraseñas cifradas con bcryptjs (rondas = 10).
- Sesiones opacas: token aleatorio (`crypto.randomBytes`) partido en dos fragmentos: uno en cookie `HttpOnly; SameSite=Strict` y el otro en cabecera `X-Session-Part`. El servidor los combina, calcula su hash (SHA-256) y lo busca en la colección `Session` (revocable, expira en 7 días con índice TTL).
- Middlewares:
  - `requireAuth` → protege rutas autenticadas.
  - `requireAdmin` → protege rutas del panel admin.
  - `validateImage` → valida rutas `/uploads/*`.

## Paso 1.4: Rutas

| Recurso | Ruta | Descripción |
|---|---|---|
| Auth | `/api/auth` | Registro, login, cambio de contraseña |
| Perfil | `/api/profile` | Consultar y modificar datos personales |
| IMC | `/api/bmi` | Cálculo derivado |
| Tracking | `/api/tracking` | Registrar, listar y eliminar pesos |
| Recetas | `/api/recipes` | Consultar recetas y detalle |
| Ejercicios | `/api/exercises` | Consultar ejercicios y detalle |
| Consejos | `/api/tips` | Consultar consejos |
| Admin | `/api/admin` | CRUD de recetas, ejercicios y consejos |

## Paso 1.5: Seed de datos

`src/scripts/seed.ts`:
- Crea (o actualiza) el **único** usuario administrador a partir de `ADMIN_EMAIL` / `ADMIN_PASSWORD`.
- Inserta contenido inicial si la colección está vacía (recetas, ejercicios y consejos).

> No existe forma de registrar usuarios administradores desde la app. El rol se asigna únicamente vía seed.

# FASE 2: Frontend

## Paso 2.1: Scaffold y tema

- Vite + React + TypeScript.
- `src/theme.ts` → MUI ThemeProvider: verde como primario, fondo claro y bordes redondeados.
- `src/main.tsx` → ThemeProvider + CssBaseline.

## Paso 2.2: Estado y servicios

- `src/context/AuthContext.tsx` → estado global de sesión (login, register, logout, fetch de usuario).
- `src/services/` → capa de API por dominio (`auth`, `recipes`, `exercises`, `tips`, `tracking`, `admin`).
- `src/utils/` → lógica pura (`bmi.ts`, `image.ts`, `colors.ts`).

## Paso 2.3: Navegación

- `src/components/NavBar.tsx` → barra superior:
  - Usuario autenticado: enlaces Mi estado / Mi progreso / Recetas / Ejercicios / Consejos + menú Admin + menú de perfil (Mi perfil, Cerrar sesión).
  - Visitante: botones Iniciar sesión / Registrarse (ocultos en `/login` y `/register` para no duplicar el formulario).
  - Responsive: drawer deslizable en móvil; la ruta activa se resalta.
- `src/components/ProtectedRoute.tsx` y `AdminRoute.tsx` → control de acceso por ruta.
- `src/App.tsx` → definición de rutas con lazy loading.

## Paso 2.4: Páginas

- **Home** → landing simple con CTA según sesión.
- **Login / Register** → formularios centrados en tarjeta.
- **Dashboard** → IMC del usuario + clasificación (Bajo peso, Normal, Sobrepeso, Obesidad) y barras de referencia.
- **Profile** → modificar datos personales y cambiar contraseña.
- **Tracking** → registrar peso/fecha, gráfico de evolución (Recharts) y tabla histórica.
- **Recipes / RecipeDetail** → tarjetas con imagen y detalle (ingredientes, preparación, nutrición).
- **Exercises / ExerciseDetail** → tarjetas con duración/dificultad y detalle (instrucciones).
- **Tips** → tarjetas de consejos.
- **Admin** → CRUD en tablas + diálogos (AdminRecipes, AdminExercises, AdminTips).

## Paso 2.5: Convenciones del frontend

- Encabezados de página con el componente compartido `PageHeader` (título + subtítulo + acción opcional).
- Colores de clasificación IMC y dificultad centralizados en `utils/colors.ts` (evitar hex hardcodeados duplicados).
- Tarjetas (`Card`) con padding uniforme; estados de carga con `CircularProgress`.
- Español en toda la interfaz; textos orientados a estudiantes.

# Buenas prácticas

- **KISS / YAGNI**: no agregar funcionalidades sin un requerimiento real.
- **DRY**: colores y lógica compartida viven en `utils/` y `components/`.
- **Seguridad**: no subir `.env` al repositorio, no exponer secretos, validar datos en frontend y backend.
