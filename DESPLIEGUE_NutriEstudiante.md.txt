# NutriEstudiante – Guía de Despliegue

> Objetivo: publicar la aplicación para que un grupo selecto de usuarios (~20-100) acceda mediante una URL, sin depender de `localhost`.
> Costo objetivo: **$0** (tiers gratuitos).
> Principios: KISS, YAGNI, DRY.

---

# 1. Arquitectura de despliegue

Un único servicio web que sirve frontend y backend (mismo origen). Esta es la opción más simple y la que la planificación ya anticipaba en FASE 4.

```
https://<app>.onrender.com            (Render free, HTTPS automático)
        │
   ┌────┴──────────────────────────────┐
   │  Servicio web único (Bun)         │
   │  backend/src/index.ts             │
   │   ├─ /api/*      → rutas API      │
   │   ├─ /uploads/*  → imágenes       │
   │   └─ /*          → frontend/dist  │
   │                    (SPA + fallback)│
   └───────────────────────────────────┘
        │
   MongoDB Atlas M0 (free, gestionado)
```

## Por qué mismo origen

- El proxy de `frontend/vite.config.ts` (`/api` y `/uploads` → `localhost:4000`) **solo funciona en desarrollo** (dev server de Vite). No existe en el build de producción.
- Sirviendo `frontend/dist` desde Express, `/api` y `/uploads` se resuelven en el mismo origen y `VITE_API_URL` usa su valor por defecto (`/api`). **No se modifica `vite.config.ts` ni el frontend.**
- Las cookies de sesión usan `SameSite=Strict` y `Secure` en producción (`backend/src/controllers/authController.ts`). Con mismo origen + HTTPS funcionan sin cambios. En dominios separados se romperían.

# 2. Cambios de código

> Estado: **ya aplicados** en `backend/src/index.ts`.

## 2.1 Servir el frontend desde Express

`backend/src/index.ts` fue modificado para:

1. Calcular la ruta del build del frontend: `frontend/dist`.
2. Servir `frontend/dist` como estático.
3. Añadir un *fallback* SPA: cualquier `GET` que no sea `/api` ni `/uploads` devuelve `index.html` (necesario porque la app usa `BrowserRouter`).

Cambios en el archivo:

```ts
import path from "node:path";

const DIST_DIR = path.resolve(import.meta.dirname, "../../frontend/dist");
```

Registrar el estático después de los middlewares base y **antes de las rutas** (o al final junto al fallback):

```ts
if (import.meta.env?.PROD === true || process.env.NODE_ENV === "production") {
  app.use(express.static(DIST_DIR));
}
```

> Nota: al usar `bun start` no existe `import.meta.env`; para simplificar, servir el estático siempre (no molesta en desarrollo). En desarrollo los `GET` a rutas no-API de Vite se sirven por el dev server de Vite (puerto 5173), por lo que nunca llegan al backend.

Middleware final (después de todas las rutas):

```ts
app.use((req, res, next) => {
  if (req.method !== "GET" || req.path.startsWith("/api") || req.path.startsWith("/uploads")) {
    next();
    return;
  }
  res.sendFile(path.join(DIST_DIR, "index.html"));
});
```

# 3. Paso a paso del despliegue

> Estado: Pasos 3.1, 3.2 y 3.3 **completados**. Credenciales en `atlas-credentials.env` (ignorado por git).

## Paso 3.1: MongoDB Atlas (free M0) — ✅ completado

1. Crear cuenta en https://www.mongodb.com/atlas.
2. Crear un **cluster M0 (free)**.
3. En *Database Access*: crear un usuario con contraseña (guardarla).
4. En *Network Access*: permitir `0.0.0.0/0` (cualquier IP) o, si Render lo provee, la IP del servicio.
5. En *Databases* → *Connect* → copiar el connection string, ej.:
   `mongodb+srv://<usuario>:<password>@cluster0.xxxxx.mongodb.net/?retryWrites=true&w=majority`

## Paso 3.2: Seed contra Atlas (una sola vez) — ✅ completado

El contenido y el admin se insertan una sola vez. Se corrió el seed **desde local** apuntando a Atlas:

```powershell
$env:MONGODB_URI="<connection string>"
$env:ADMIN_EMAIL="<email admin>"
$env:ADMIN_PASSWORD="<password admin>"
bun run seed    # ejecutar dentro de backend/
```

Verificado en Atlas: `users` (1, admin), `recipes` (15), `exercises` (12), `tips` (8).

> **Importante:** el seed crea el admin solo si no existe; si existe no actualiza su contraseña. Por eso las credenciales del admin se definieron en este paso (están en `atlas-credentials.env`).

### Nota: DNS SRV en Windows local

En la red local, Bun falló resolviendo `mongodb+srv://` (`querySrv ECONNREFUSED`), aunque `Resolve-DnsName` resuelve bien. En Render (Linux) el SRV funciona sin problema. Si el SRV fallara localmente, usar la URI completa del replica set (obtenida con `Resolve-DnsName` + `hello`), que evita la consulta SRV:

```
mongodb://<user>:<pass>@<shard-00-00>.mongodb.net:27017,<shard-00-01>.mongodb.net:27017,<shard-00-02>.mongodb.net:27017/nutriestudiante?ssl=true&authSource=admin&replicaSet=<nombre>&retryWrites=true&w=majority
```

## Paso 3.3: Commit y push del código e imágenes — ✅ completado

Antes de crear el servicio en Render, subir a GitHub los cambios de código y las imágenes:

1. Verificar que `backend/uploads/` tenga las 15 imágenes y que el build compile:
   ```bash
   bun --cwd backend typecheck
   bun --cwd frontend build
   ```
2. Commitear y hacer push (incluye el código modificado, las imágenes nuevas y la carpeta `assets/` obsoleta):
   ```bash
   git add backend/src frontend/src backend/uploads assets
   git commit -m "Despliegue: servir frontend desde Express + imágenes"
   git push origin main
   ```

## Paso 3.4: Render (Web Service free)

1. Crear cuenta en https://render.com (login con GitHub).
2. *New* → *Web Service* → conectar el repo `MasterCarl109/NutriEstudiante-C`.
3. Configuración:

   | Build Command | `bun install && bun --cwd backend install && bun --cwd frontend install && bun --cwd frontend build` |
   | Start Command | `bun --cwd backend start` |
   | Instance Type | Free |

4. En *Environment Variables* (valores concretos en `atlas-credentials.env`):

   | Variable | Valor |

# 5. Limitaciones del free tier (aceptadas)

- El servicio **duerme** tras ~15 min sin tráfico y la primera visita tarda ~1 min en despertar. Aceptable para un grupo selecto.
- 512 MB de RAM y 512 MB de almacenamiento (Atlas M0 también limita a 512 MB). Suficiente para el alcance actual.
- Si el proyecto crece, migrar a un plan de pago o a un VPS no requiere cambios de arquitectura.

---

# 6. Notas de seguridad

- `backend/.env` no se sube al repositorio (ignorado por `.gitignore`). Los secretos viven solo en las variables de entorno de Render.
- No exponer `ADMIN_EMAIL` / `ADMIN_PASSWORD` en el código ni en el repo.
- `NODE_ENV=production` activa las cookies `Secure` (solo HTTPS). Sin HTTPS la sesión no persiste.
- Validar antes de cada deploy:
  ```bash
  bun --cwd backend typecheck
  bun --cwd frontend lint
  bun --cwd frontend build
  ```

# 7. Redeploys futuros

Cada vez que haya cambios en `main`:

1. Ejecutar las verificaciones del punto 6.
2. Commitear y hacer push.
3. En Render, *Manual Deploy* → *Deploy latest commit* (o activar auto-deploy).
4. No es necesario re-correr el seed (el contenido ya existe en Atlas; el seed no sobrescribe).
